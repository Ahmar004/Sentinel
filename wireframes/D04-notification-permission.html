  1. The explanation comes before the request, not after. The dialog states exactly what a notification will contain and when it fires before any browser permission popup appears, because a bare permission prompt with no context is usually refused, and a refusal cannot be undone by asking again louder. FR5.5
  2. It is triggered by a real alert, not by first load. A-1042's toast sits visibly behind the scrim so the request lands at the moment its value is obvious, not before the user has seen Sentinel do anything worth being notified about.
  3. The audible tone toggle lives in the same dialog, not a second screen. Both settings a user might want to control on first contact with notifications - whether they arrive at all, and whether they make a sound - are decided together.
  4. SMS and email are named and ruled out in the dialog's own words. This is the interface half of decision D4: every paid delivery gateway is excluded, so the honest statement is that in-app and this one browser channel are all there is. FR5.5
  5. Not now is type="button", Enable is type="submit", on a real <form onsubmit> calling event.preventDefault(). Enter submits, Esc cancels, and focus is trapped in the dialog while open and returned to the toast or the menu item that opened it once it closes.
  6. Mobile carries the identical two sentences and the same toggle, shortened only in layout, because the SMS/email boundary and the tone setting are not content a coordinator's device can afford to drop.
  7. Available afterwards from the user menu, unchanged. The second context shows the exact same dialog reached from "Notification settings", proving there is one definition of this surface rather than a fresh copy written for the reopened case. On reopen, the toggle reflects whatever was last chosen rather than defaulting back on. FR5.5
