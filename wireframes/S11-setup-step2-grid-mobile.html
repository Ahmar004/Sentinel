Fewer, coarser cells - a bottleneck narrower than 10 m would blend into its neighbours and stop being resolvable.
  1. Cell size is a small closed set, not a free number an administrator could mistune. 2, 5 and 10 m as one-tap chips, with the exact value shown read-only beside them; 5 m is Riverside Arena's fixed value from srs.md 2.7. FR9.2
  2. The preview regenerates from the same value the chips set - there is one source of truth for cell size, never a separate apply step that could let the count and the picture disagree. FR9.2
  3. 60 x 40 = 2400 cells is computed, not typed. This is the acceptance test in srs.md FR9.2 made visible: a 5 m cell size over the fixed 300 m by 200 m extent produces exactly this count. FR9.2
  4. The count visibly changes with the size. The second device is the same step at 10 m: 30 x 20 = 600 cells, with visibly coarser grid lines on the same plan image, proving the count is derived rather than a fixed label. FR9.2
  5. Origin is the south-west corner, offset in metres. Riverside Arena uses 0 m east and 0 m north; the marker on the preview would move if either were non-zero, so an offset is visible, not just numeric. FR9.2
  6. The grid preview uses plain lines, never a live cell treatment. No obs-* or band-* class appears here - this screen shows the plan and the grid, never observed data, so it can never read as a live map.
  7. The cell identifier form is decided here. C-<col>-<row> zero padded to three digits, because every later screen in the product references cells by this identifier. FR9.2
  8. Continue is the form's submit action; Enter submits and Esc cancels the wizard per the shared wizard shell.
